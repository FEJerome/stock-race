## 1. 概述

### 1.1 背景

本项目采用六服务分布式架构，随着功能扩展，服务间的调用关系变得复杂。本文档旨在梳理现有调用链，设计一个成熟可靠、扩展性好的服务通信架构。

### 1.2 当前服务矩阵

| 服务 | 技术栈 | 端口 | 主要职责 | 状态 |
|------|--------|------|----------|------|
| **frontend** | React 18 + TypeScript | 3000 | Web用户界面 | 已完成 |
| **miniprogram** | UniApp + Vue 3 | - | 微信小程序 | 已完成 |
| **backend** | Node.js + Express | 3001 | API网关、业务编排 | 已完成 |
| **ai-service** | Python + FastAPI | 8000 | AI决策、模型适配 | 已完成 |
| **data-service** | Python + FastAPI | 8001 | 数据采集、行情服务 | 已完成 |
| **news-service** | Python + FastAPI | 8002 | 新闻采集、情感分析 | 开发中 |

### 2.2 核心设计原则

#### 2.2.1 Backend for Frontend (BFF) 模式

Backend 不再直接透传请求，而是作为 **BFF 层**，为前端提供聚合后的数据：

```javascript
// BFF 职责定义
┌────────────────────────────────────────┐
│  Backend (BFF Layer)                   │
│                                        │
│  1. 认证鉴权 (Auth)                     │
│     └─ 所有请求必须经过 JWT 验证        │
│                                        │
│  2. 服务编排 (Orchestration)            │
│     └─ 聚合多个服务的数据返回给前端      │
│                                        │
│  3. 协议转换 (Protocol Translation)     │
│     └─ REST ↔ gRPC/内部协议             │
│                                        │
│  4. 缓存层 (Caching)                    │
│     └─ Redis 缓存常用数据               │
│                                        │
│  5. 限流熔断 (Circuit Breaker)          │
│     └─ 保护下游服务                     │
└────────────────────────────────────────┘
```

**数据聚合示例**：
```javascript
// DecisionAggregator.js 示例
async getAIDecisionWithContext(accountId, stockCode) {
    // 并行获取所需数据
    const [marketData, newsData, portfolioData] = await Promise.all([
        this.dataService.getStockQuote(stockCode),
        this.newsService.getStockSentiment(stockCode),
        this.portfolioService.getPosition(accountId, stockCode)
    ]);

    // 调用 AI Service 进行决策
    const decision = await this.aiService.requestDecision({
        accountId,
        stockCode,
        marketData,
        newsSentiment: newsData,
        portfolioData
    });

    return {
        decision,
        context: { marketSnapshot, sentiment, portfolio }
    };
}
```

#### 2.2.2 服务间通信策略

| 场景 | 通信方式 | 原因 |
|------|----------|------|
| 实时查询（行情、决策） | **同步 HTTP** | 需要立即响应 |
| 数据同步（交易记录） | **异步消息** | 解耦、削峰 |
| 事件通知（价格预警） | **WebSocket/SSE** | 实时推送 |

```
┌─────────────────────────────────────────────────────────┐
│                    同步调用 (HTTP/gRPC)                  │
│  ┌─────────────┐      ┌─────────────┐                   │
│  │   Backend   │◄────►│  AI Service │                   │
│  └─────────────┘      └─────────────┘                   │
│         │                                             │
│         ▼                                             │
│  ┌─────────────┐      ┌─────────────┐                  │
│  │ Data Service│◄────►│ News Service│                  │
│  └─────────────┘      └─────────────┘                  │
└─────────────────────────────────────────────────────────┘

┌─────────────────────────────────────────────────────────┐
│                   异步调用 (消息队列)                     │
│   交易事件 ──► [Redis Stream] ──► 风控服务              │
│   价格更新 ──► [Redis Pub/Sub] ──► 前端推送             │
│   AI决策请求 ──► [Bull Queue] ──► 异步处理              │

```

## 4. 关键改进点

### 4.1 与当前架构的对比

| 改进项 | 当前方案 | 推荐方案 | 预期收益 |
|--------|----------|----------|----------|
| **服务发现** | 硬编码URL | 服务注册中心 | 动态扩缩容 |
| **负载均衡** | 无 | 客户端负载均衡 | 提高可用性 |
| **熔断降级** | 各服务独立 | 统一熔断管理 | 快速失败保护 |
| **数据聚合** | 前端多次请求 | BFF 聚合 | 减少请求数 |
| **缓存策略** | 各服务独立 | 统一缓存层 | 减少重复计算 |
| **监控链路** | 日志分散 | 分布式追踪 | 快速定位问题 |

### 4.2 设计亮点

1. **分层清晰**：客户端层 → API网关 → BFF层 → 领域服务 → 基础设施
2. **职责单一**：每个服务有明确的边界，避免功能重叠
3. **松耦合**：服务间通过标准接口通信，便于独立演进
4. **高可用**：熔断、降级、重试机制保障系统稳定性
5. **可观测**：全链路监控，便于问题排查
