# 动态权重算法与智能调度器详解

## 🌊 比喻：像水一样流动的数据源调度

想象我们的6个数据源就像6条不同特性的河流：

- **新浪财经** = 长江（最宽、最稳、流速适中）
- **腾讯财经** = 黄河（水量大、但偶尔有泥沙）
- **AkShare** = 山间小溪（最近、但容易被石头堵住）
- **东方财富** = 人工运河（可控、但容量有限）
- **Baostock** = 地下暗河（稳定、但速度慢）
- **Tushare** = 限量水库（有配额限制）

**动态权重算法**就像一个智能水闸管理员，根据每条河的实时状态调整开闸大小。

---

## 📊 动态权重计算公式

```
最终权重 = 基础权重
         × 成功率因子
         × 延迟因子
         × 限流因子
         × 健康因子
         × 时段因子
```

### 1. 成功率因子 - 学习能力

```python
if 成功率 >= 99%:    因子 = 1.2  (奖励20%)
if 成功率 >= 95%:    因子 = 1.1  (奖励10%)
if 成功率 >= 90%:    因子 = 1.0  (正常)
if 成功率 >= 80%:    因子 = 0.8  (惩罚20%)
if 成功率 >= 60%:    因子 = 0.6  (惩罚40%)
if 成功率 < 60%:     因子 = 0.5  (惩罚50%)
```

**实际案例：**
- AkShare连续5次成功：权重从1.0 → 1.2
- 腾讯连续3次失败：权重从0.8 → 0.5
- 系统立即减少失败源的流量，增加成功源的流量

### 2. 延迟因子 - 速度感知

```python
if 延迟 < 100ms:     因子 = 1.1  (火箭速度，奖励)
if 延迟 < 300ms:     因子 = 1.0  (正常速度)
if 延迟 < 500ms:     因子 = 0.9  (稍慢)
if 延迟 < 1000ms:    因子 = 0.7  (慢速)
if 延迟 >= 1000ms:   因子 = 0.5  (龟速，惩罚)
```

**实际案例：**
- 新浪响应200ms：权重保持1.0
- AkShare突然延迟2秒（被限流）：权重降至0.5
- 系统自动将请求路由到更快的腾讯

### 3. 限流因子 - 配额管理

```python
剩余配额 > 50%:     因子 = 1.0  (充足)
剩余配额 30-50%:    因子 = 0.8  (紧张)
剩余配额 10-30%:    因子 = 0.5  (告急)
剩余配额 < 10%:     因子 = 0.1  (几乎耗尽)
```

**实际案例：**
- Tushare每日限额400次，已用350次：
- 剩余12.5%，权重降至0.1
- 系统几乎不再使用Tushare，保留配额给紧急需求

### 4. 健康因子 - 体检报告

```python
健康分数 = 成功率×70 - 连续错误×10 - 限流命中×5 + 低延迟奖励10

健康分数 90-100:    因子 = 1.0  (健康)
健康分数 70-90:     因子 = 0.8  (亚健康)
健康分数 50-70:     因子 = 0.6  (生病)
健康分数 < 50:      因子 = 0.0  (隔离/停用)
```

**实际案例：**
- AkShare连续10次错误：健康分降至30，因子0.0
- 系统自动停用AkShare，标记为"隔离"
- 5分钟后自动尝试恢复

### 5. 时段因子 - 生物钟

```python
交易时段 (9:30-11:30, 13:00-15:00):     因子 = 1.2  (全力运行)
开盘前30分钟 (9:00-9:30):              因子 = 0.8  (预热)
午盘休息 (11:30-13:00):                 因子 = 0.9  (小憩)
收盘后1小时 (15:00-16:00):              因子 = 0.8  (收尾)
夜间 (16:00-9:00):                      因子 = 0.6  (休眠)
```

**实际案例：**
- 9:30开盘瞬间，所有源权重+20%
- 系统优先保证交易时段的数据质量
- 夜间减少请求，节省配额

## 🎯 智能调度器 - 交通警察

想象6个数据源是6条高速公路，智能调度器就是交通指挥中心：

### 1. 请求队列系统

```
                    ┌─────────────────┐
                    │   请求队列池     │
                    └────────┬────────┘
                             │
        ┌────────────────────┼────────────────────┐
        │                    │                    │
   ┌────▼────┐          ┌────▼────┐          ┌────▼────┐
   │新浪队列 │          │腾讯队列 │          │AkShare  │
   │ max:480 │          │ max:960 │          │ max:400 │
   └────┬────┘          └────┬────┘          └────┬────┘
        │                    │                    │
   ┌────▼────┐          ┌────▼────┐          ┌────▼────┐
   │交通灯   │          │交通灯   │          │交通灯   │
   │绿灯/红灯│          │绿灯/红灯│          │绿灯/红灯│
   └────┬────┘          └────┬────┘          └────┬────┘
        │                    │                    │
   ┌────▼────┐          ┌────▼────┐          ┌────▼────┐
   │新浪服务 │          │腾讯服务 │          │AkShare  │
   └─────────┘          └─────────┘          └─────────┘
```

**工作流程：**
1. 每个请求进入对应的队列
2. 交通灯检查当前流速（最近1分钟请求数）
3. 如果超过限制，红灯亮起，请求等待
4. 绿灯时，请求通过，记录时间戳

### 2. 自适应等待算法

```python
class RequestScheduler:
    async def schedule_request(self, source_name, request_func):
        config = RATE_LIMIT_CONFIG[source_name]

        # 检查是否需要等待
        while True:
            recent_count = self.get_recent_request_count(source_name, seconds=60)

            if recent_count < config["requests_per_minute"] * 0.9:
                # 绿灯：直接通过
                break
            elif recent_count < config["requests_per_minute"]:
                # 黄灯：等待一小会儿
                await asyncio.sleep(0.1)
            else:
                # 红灯：计算需要等待的时间
                oldest_request = self.get_oldest_request(source_name)
                wait_time = 60 - (now - oldest_request) + 0.1
                logger.warning(f"{source_name} 限流，等待 {wait_time:.2f}秒")
                await asyncio.sleep(wait_time)

        # 记录请求时间
        self.request_timestamps[source_name].append(time.time())

        # 执行请求
        return await request_func()
```

**实际案例：**
- 新浪已用450/480请求（93%），新请求到来
- 交通灯：黄灯，等待0.1秒
- 60秒窗口滑动后，最老的请求过期
- 新请求成功通过
