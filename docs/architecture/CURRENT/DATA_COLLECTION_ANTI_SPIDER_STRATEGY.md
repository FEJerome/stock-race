# 反爬机制下的分层采集优化方案

**文档版本**: 1.0
**创建时间**: 2026-02-13
**适用范围**: Market Data Service 全量A股数据采集

---

## 📋 问题背景

在10分钟全量A股数据采集测试中，发现以下问题：

| 现象 | 根因分析 |
|------|----------|
| 直连Sina成功，Router失败 | 容器网络DNS/出口受限 |
| 所有数据源返回空 | 批量请求150只触发反爬机制 |
| AkShare连接被重置 | 容器网络MTU或防火墙限制 |

**核心矛盾**: 设计容量 > 实际反爬容忍度

---

## 🎯 优化策略总览

```
┌─────────────────────────────────────────────────────────────────┐
│                  修正版分层采集架构（反爬友好）                        │
├─────────────────────────────────────────────────────────────────┤
│                                                                  │
│  层级        股票数     延迟      数据源策略                        │

│                                                                  │
│  总覆盖: 5000只（全量A股）                                        │
│  核心原则: 分批次 + 降频 + 多源分散                                │
└─────────────────────────────────────────────────────────────────┘
```

## 🔧 实施变更

### 1. 容器网络优化 (docker-compose.integration.yml)

```yaml
market-data-service:
  # 网络优化 - 解决容器DNS和连接问题
  dns:
    - 8.8.8.8
    - 114.114.114.114
  sysctls:
    - net.ipv4.tcp_keepalive_time=60
    - net.ipv4.tcp_keepalive_intvl=10
    - net.ipv4.tcp_keepalive_probes=6

  # 采集策略环境变量
  environment:
    - BATCH_SIZE=80              # 批次大小: 80只
    - BATCH_INTERVAL=1.5         # 批次间隔: 1.5秒
    - HIGH_FREQ_STOCKS=100       # 高频层: 100只
    - HIGH_FREQ_INTERVAL=10      # 高频间隔: 10秒
    - MID_FREQ_STOCKS=400        # 中频层: 400只
    - MID_FREQ_INTERVAL=30       # 中频间隔: 30秒
    - LOW_FREQ_STOCKS=4500       # 低频层: 4500只
    - LOW_FREQ_INTERVAL=60       # 低频间隔: 60秒
```

### 2. 批次大小调整

| 文件 | 原配置 | 新配置 | 说明 |
|------|--------|--------|------|
| `router.py` | 50只/段 | 80只/段 | 分段策略 |
| `config.py` | 100只 | 80只 | 全局默认 |
| `enhanced_data_service.py` | 50只 | 80只 | 服务层 |

**为什么选择80只？**
- 新浪接口URL长度限制约2000字符
- 80只股票代码约占用: 80 × 10字符 = 800字符
- 预留空间给参数和Header
- 实际测试验证安全阈值

### 3. 分层配置新增 (config.py)

```python
# 分层采集配置 - 基于反爬机制优化
HIGH_FREQ_STOCKS: int = 100      # 高频层100只
HIGH_FREQ_INTERVAL: int = 10      # 10秒
MID_FREQ_STOCKS: int = 400       # 中频层400只
MID_FREQ_INTERVAL: int = 30       # 30秒
LOW_FREQ_STOCKS: int = 4500      # 低频层4500只
LOW_FREQ_INTERVAL: int = 60       # 60秒
```

## 📊 理论容量验证

### 高频层 (100只/10秒)

```
数据源: 新浪(50) + 腾讯(50)
请求方式: 双源并行
批次: 50/80 = 1批次
频率: 6次/分钟
容量利用率: 6/480(新浪) + 6/960(腾讯) = 1.9%
✅ 远低于限制，安全
```

### 中频层 (400只/30秒)

```
数据源: 新浪 + 腾讯 + AkShare + 东方财富
请求方式: 4源轮询
批次: 400/80 = 5批次
频率: 2轮/分钟 × 5批次 = 10次/源/分钟
容量利用率:
  - 新浪: 10/480 = 2.1%
  - 腾讯: 10/960 = 1.0%
  - AkShare: 10/400 = 2.5%
  - 东方财富: 10/240 = 4.2%
✅ 所有源都在安全范围内
```

### 低频层 (4500只/60秒)

```
数据源: 新浪 + 腾讯 + AkShare + 东方财富 + Baostock
请求方式: 5源并行分片
分配: 4500/5 = 900只/源
批次: 900/80 = 12批次/源/分钟
容量利用率:
  - 新浪: 12/480 = 2.5%
  - 腾讯: 12/960 = 1.3%
  - AkShare: 12/400 = 3.0%
  - 东方财富: 12/240 = 5.0%
  - Baostock: 12/240 = 5.0%
✅ 全源在安全范围内，东财/Baostock接近警戒线
```

## ⚠️ 风险与应对

### 风险1: 低频层东方财富/Baostock接近限制

**应对策略**:
- 监控实际请求频率
- 如触发限流，启用降级模式:
  - 低频层间隔从60秒延长到90秒
  - 股票数量从4500减少到4000

### 风险2: 高频层100只无法满足业务需求

**应对策略**:
- 高频层扩展到150只需要12.5秒间隔
- 或增加数据源（需申请新API）
- 或采用推拉结合: 高频层主动推送 + 用户订阅优先

### 风险3: 容器网络仍不稳定

**应对策略**:
- 增加网络诊断和健康检查
- 预留宿主机直接运行模式
- 配置代理服务器作为备用出口
