### 1.2 核心设计原则

1. **数据主权明确**：每个服务只写入自己负责的数据，通过API读取其他服务数据
2. **统一事件总线**：服务间通过Redis Pub/Sub + Streams松耦合通信
3. **分层存储**：热/温/冷数据根据访问频率和成本存储在不同介质
4. **渐进演进**：从简单开始，预留扩展点，不提前过度设计

#### 数据生命周期（News Service专用）

| 阶段 | 存储 | 内容 | TTL | 用途 |
|------|------|------|-----|------|
| **原始** | Redis Stream | 完整新闻文本 | 1小时 | 临时缓冲，给DeepSeek处理 |
| **热数据** | Redis Hash | 结构化情报（500字节） | 24小时 | AI实时决策 |
| **温数据** | PostgreSQL | 浓缩情报（100字节） | 7天 | 趋势分析、复盘 |
| **冷数据** | 不存储 | - | - | 不保留，降低成本 |

#### PostgreSQL表结构

```sql
-- 情报表（只存浓缩后的数据）
CREATE TABLE stock_intelligence (
    id SERIAL PRIMARY KEY,
    stock_code VARCHAR(10) NOT NULL,           -- 股票代码
    sentiment VARCHAR(10) CHECK (sentiment IN ('positive', 'negative', 'neutral')),
    sentiment_score DECIMAL(3,2),               -- 情感置信度 0.00-1.00
    summary VARCHAR(100) NOT NULL,              -- 摘要，严格控制100字符
    importance INT CHECK (importance BETWEEN 1 AND 10),
    sectors VARCHAR(50)[],                      -- 关联板块
    is_breaking BOOLEAN DEFAULT FALSE,          -- 是否突发
    source VARCHAR(50),                         -- 来源
    created_at TIMESTAMP DEFAULT NOW(),
    expires_at TIMESTAMP DEFAULT NOW() + INTERVAL '7 days',  -- 自动过期
    INDEX idx_stock_code (stock_code),
    INDEX idx_created_at (created_at),
    INDEX idx_expires_at (expires_at)           -- 用于自动清理
);

-- 自动清理过期数据
CREATE OR REPLACE FUNCTION clean_expired_intelligence()
RETURNS void AS $$
BEGIN
    DELETE FROM stock_intelligence WHERE expires_at < NOW();
END;
$$ LANGUAGE plpgsql;
```

## 9. 附录：新闻服务资源预估

### 9.1 方案对比

| 维度 | ES方案（已废弃） | 精简方案（当前） | 节省 |
|------|-----------------|-----------------|------|
| **存储** | 10-50GB | 500MB-1GB | 95%+ |
| **内存** | 4-8GB | 1-2GB | 75%+ |
| **CPU** | 4核 | 2核 | 50% |
| **月成本** | ¥500-1000 | ¥100-200 | 80%+ |
| **查询延迟** | 50-100ms | 5-10ms（Redis） | 90%+ |
| **Token可控性** | 差（全文存储） | 优（摘要存储） | - |

### 9.2 精简方案资源需求

#### 存储空间计算

```
每日原始新闻：25MB
↓ DeepSeek处理
每日结构化情报：500字节 × 3000条 = 1.5MB

7天数据量：
- Redis热数据：1.5MB × 7 = 10.5MB
- PostgreSQL温数据：1.5MB × 7 = 10.5MB
- 建议配置：1GB 存储空间（预留增长）
```

#### 内存需求

```
News Service 进程：~500MB
Redis 数据：~20MB
PostgreSQL 连接：~100MB

总内存需求：1-2GB
```

#### DeepSeek Token 消耗预估

```
每日处理新闻：3000条
每条处理消耗：~2000 tokens（输入+输出）
每日总消耗：3000 × 2000 = 6,000,000 tokens

成本预估（按 DeepSeek V3 价格）：
- 输入：4M tokens × ¥0.001/M = ¥4
- 输出：2M tokens × ¥0.002/M = ¥4
- 每日成本：~¥8
- 每月成本：~¥240
```

### 9.3 配置建议

#### 开发环境

```yaml
# docker-compose.yml
services:
  news-service:
    image: news-service:latest
    environment:
      - DEEPSEEK_API_KEY=${DEEPSEEK_API_KEY}
      - REDIS_URL=redis://redis:6379/2
      - PG_URL=postgresql://user:pass@postgres:5432/news
    deploy:
      resources:
        limits:
          memory: 1G
          cpus: '1.0'
```

#### 生产环境

```yaml
services:
  news-service:
    replicas: 2  # 双实例保障可用性
    deploy:
      resources:
        limits:
          memory: 2G
          cpus: '2.0'
    environment:
      - DEEPSEAK_RATE_LIMIT=100/min  # 控制API调用频率
```

### 9.4 关键优化点

1. **批处理**：新闻积攒到10条后批量调用DeepSeek，降低API调用次数
2. **去重缓存**：使用Redis记录已处理新闻的hash，24小时内不重复处理
3. **降级策略**：DeepSeek不可用时，直接丢弃新闻（保证系统稳定）
4. **流控保护**：限制DeepSeek调用频率，防止API限额超限
