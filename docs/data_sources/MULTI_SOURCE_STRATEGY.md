## 🎯 方案概述

本方案旨在构建一个基于AkShare、Baostock、Tushare基础版的多维度A股股票数据采集系统。通过智能数据源选择、分层缓存策略和优化调度算法，在免费数据源限制下实现最低数据延迟和最高数据可靠性。

### 1. 实时数据采集策略（高频层）

#### 目标：最小数据延迟（<5秒）

**数据源优先级**：
1. **AkShare**（实时数据接口） - 主实时数据源
2. **Tushare**（实时报价） - 备用实时数据源
3. **组合数据源** - 多个AkShare源站组合

**调度策略**：
- **交易时间**（9:30-11:30, 13:00-15:00）：每3秒轮询一次
- **集合竞价**（9:15-9:25）：每5秒轮询一次
- **非交易时间**：每60秒轮询一次

**批量处理**：
- 按板块分组获取（每次50-100只股票）
- 智能分批避免触发频率限制
- 并行获取不同板块数据

### 2. 历史数据采集策略（低频层）

#### 目标：数据完整性和质量

**数据源优先级**：
1. **Tushare**（历史K线） - 主历史数据源（数据质量最高）
2. **Baostock**（历史K线） - 备用历史数据源
3. **AkShare**（历史数据） - 补充数据源

**更新策略**：
- **日线数据**：每日收盘后（15:30）自动更新
- **周线/月线**：每周/每月第一个交易日更新
- **财务数据**：季度财报发布后更新

**增量更新**：
- 仅获取新增数据，避免重复下载
- 断点续传支持
- 数据验证和修复机制

### 3. 批量数据采集策略（计划任务层）

#### 目标：基础数据维护

**采集内容**：
- 股票列表和基本信息
- 行业分类和板块信息
- 指数成分股和权重
- 公司基本资料

**调度频率**：
- 每日凌晨2:00更新股票列表
- 每周一凌晨3:00更新行业分类
- 每月第一个交易日更新指数成分

## 💾 智能缓存策略

### 缓存分层设计

#### 1. 内存缓存（L1缓存）
- **存储位置**：Redis内存数据库
- **缓存内容**：实时报价、热门股票数据
- **过期策略**：
  - 实时数据：5-30秒（根据数据源实时性调整）
  - 热门股票：1-5分钟（访问频率自适应）
  - 股票信息：1小时（相对稳定数据）

#### 2. 磁盘缓存（L2缓存）
- **存储位置**：TimescaleDB时序数据库
- **缓存内容**：历史K线数据、日频数据
- **过期策略**：
  - 日线数据：永久存储（历史数据）
  - 分时数据：保留30天
  - 分钟数据：保留7天

#### 3. 文件缓存（L3缓存）
- **存储位置**：本地Parquet/CSV文件
- **缓存内容**：备份数据、原始API响应
- **过期策略**：
  - 原始响应：保留24小时（用于调试）
  - 备份数据：保留7天

### 缓存有效性管理

#### 自适应TTL算法
```python
def calculate_adaptive_ttl(data_type, access_frequency, data_freshness):
    """
    根据数据类型、访问频率和数据新鲜度计算自适应TTL

    参数:
        data_type: 数据类型（实时报价、历史K线、股票信息等）
        access_frequency: 访问频率（次/小时）
        data_freshness: 数据新鲜度（数据更新时间间隔）

    返回:
        ttl_seconds: 缓存过期时间（秒）
    """
    base_ttl = {
        'realtime_quote': 5,      # 实时报价基础TTL
        'historical_kline': 3600, # 历史K线基础TTL
        'stock_info': 1800,       # 股票信息基础TTL
        'industry_data': 86400    # 行业数据基础TTL
    }

    # 访问频率因子（访问越频繁，TTL越短）
    freq_factor = max(0.1, min(2.0, 100 / (access_frequency + 1)))

    # 数据新鲜度因子（数据更新越频繁，TTL越短）
    freshness_factor = max(0.5, min(3.0, 300 / (data_freshness + 1)))

    ttl = base_ttl.get(data_type, 300) * freq_factor * freshness_factor

    # 限制在合理范围内
    return min(max(ttl, 1), 86400)  # 1秒到24小时之间
```

#### 缓存预热策略
1. **预测性预热**：基于历史访问模式预加载可能需要的股票数据
2. **交易时间预热**：交易开始前预加载热门板块股票
3. **事件驱动预热**：重大新闻事件相关股票预加载

#### 缓存清理策略
1. **LRU淘汰**：内存缓存使用LRU算法
2. **时间淘汰**：按过期时间自动清理
3. **手动清理**：API支持手动清理指定缓存

## ⚡ 最小延迟方案

### 免费限制下的优化策略

#### 1. 数据源并行请求
```
策略：将股票列表分割到不同数据源并行获取
优势：利用多个数据源的免费额度
实现：
  - 股票列表按数据源免费额度比例分割
  - 并行向多个数据源发起请求
  - 结果合并和数据一致性验证
```

#### 2. 增量更新机制
```
策略：仅获取变化的数据，减少数据量
优势：显著降低API调用次数和数据传输量
实现：
  - 记录上次获取的数据版本
  - 仅请求自上次更新以来的变化
  - 本地数据补全和验证
```

#### 3. 智能重试和退避
```
策略：失败请求的智能重试机制
优势：提高数据获取成功率，减少等待时间
实现：
  - 指数退避重试（1s, 2s, 4s, 8s...）
  - 数据源切换重试（主源失败切备用源）
  - 部分成功处理（获取部分数据而非全部失败）
```

#### 4. 实时数据流模拟
```
策略：在无法获取真正实时数据时模拟数据流
优势：提供接近实时的用户体验
实现：
  - 基于最后已知价格+随机波动模拟
  - 结合大盘指数变动调整
  - 下次真实数据到达时校正
```

### 预期延迟指标

| 数据类型 | 目标延迟 | 保证延迟 | 数据源 |
|---------|---------|---------|--------|
| 实时报价 | <5秒 | <10秒 | AkShare为主，Tushare备用 |
| 分时数据 | <10秒 | <30秒 | 多源组合 |
| 日K数据 | <60秒 | <5分钟 | Tushare/Baostock |
| 历史数据 | 立即（缓存） | <2秒 | 缓存优先 |
