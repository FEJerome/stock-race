## 一、合规风险遗漏（🔴 高优先级）

### 1.1 策略粒度分级机制在架构中完全缺失

**PRD 依据**：PRD §4.2.2 明确定义了"策略收集粒度分级"（细/中/粗），且标注为 🟢 已冻结。

**consultation-material.html 依据**：§1.3 策略输入边界机制是合规咨询的核心论点——"AI仅执行用户明确预设的规则，而非主动提供投资建议"。

**当前问题**：
- ARCHITECTURE.md 的策略收集部分（§3.3 CreateAgentRequest）只有五维度字段定义，**完全没有**粒度检测层的架构设计
- 缺少"粗粒度→拒绝执行→引导细化"的流程设计
- 缺少"AI回复合规检查层过滤"的架构组件
- IMPLEMENTATION_PLAN.md §4.1 策略收集对话仅有"五维度收集"，**没有**粒度分级的任务项

**建议**：
```
services/
├── strategy_service.py          # 现有
├── strategy_compliance.py       # 新增：粒度检测 + 合规检查
│   ├── GranularityDetector      # 粒度级别检测（细/中/粗）
│   ├── ComplianceFilter         # AI回复合规过滤
│   └── GuidanceEngine           # 粗→中→细引导逻辑
```
在 IMPLEMENTATION_PLAN Phase 1.3 中新增：
- `B-1.3.x` 粒度检测服务（4h）
- `B-1.3.x` 合规过滤层（4h）
- `F-1.3.x` 粒度检测提示UI（⚠️/✅ 标志）（2h）

### 1.2 合规声明体系在架构中无体现

**consultation-material.html 依据**：附录B 核心隔离声明、§2.1 工具vs服务边界、§2.2 排行榜免责声明，均是产品合规的基石。

**PRD 依据**：§4.1.4 合规声明明确要求——"所有涉及收益率的页面标注虚拟交易声明"、"禁用诱导性词汇"。

**当前问题**：
- ARCHITECTURE.md 前端架构中**没有**合规声明组件
- 没有"全局免责声明中间件"或"收益页面合规装饰器"的设计
- 排行榜（F-1.3.9）没有标注"T+1延迟展示"、"强制风险指标展示"等合规措施

**建议**：
- 前端新增 `components/compliance/` 目录：`DisclaimerBanner.vue`、`RiskWarning.vue`
- 排行榜组件嵌入免责声明和风险指标（最大回撤、夏普比率）
- 后端新增合规中间件：所有涉及收益数据的API响应附带免责声明字段

### 1.3 AI决策输出的合规边界未定义

**consultation-material.html 依据**：§2.1 明确区分——"AI仅解释'为何执行用户已明确的策略'"，不可主动荐股。

**PRD 依据**：§4.2.2 粒度分级合规设计中——"禁止 AI 在无明确范围时自主大量选股"。

**当前问题**：
- ARCHITECTURE.md §5.3.6 Decision 模型中有 `action: buy/sell/hold/watch` 和 `symbol`，但**没有**定义AI如何被约束只操作"用户预设范围内的标的"
- DecisionContext 中缺少"允许交易标的白名单"字段
- 缺少AI输出的合规后置过滤（检查AI是否推荐了用户未指定的股票）

**建议**：
- DecisionContext 增加 `allowed_symbols: List[str]` 字段（源自用户策略中指定的标的）
- 新增 `DecisionComplianceValidator`：校验AI输出的symbol是否在允许范围内
- Decision 模型增加 `compliance_checked: bool` 字段

## 二、PRD 对齐偏差（🟡 中优先级）

### 2.1 虚拟资金名称不统一

**PRD 依据**：§8.1 术语表明确定义"投资研究点数"为虚拟资金名称。

**consultation-material.html 依据**：§1.4 专门用"投资研究点数"强调非真实资金性质。

**当前问题**：
- ARCHITECTURE.md 中使用 `initial_capital`、`current_capital` 等字段名
- 前端/API中使用"初始资金"等措辞
- 缺少从"资金"到"投资研究点数"的术语映射

**建议**：
- API层对外展示时使用"投资研究点数"（`research_points`）
- 内部计算层可保留 `capital` 语义，但对外接口和前端统一使用PRD术语
- 这是合规层面的措辞要求，不仅是命名偏好

### 2.2 交易时间校验逻辑不完整

**PRD 依据**：§4.3.2 明确"A股交易日：09:30-11:30, 13:00-15:00"。

**当前问题**：
- ARCHITECTURE.md §5.2 交易执行流程提到"检查交易时间"
- 但**没有**法定节假日/调休日历的架构设计
- PRD §4.5 待确认问题中也提到"长假交易日历维护"

**建议**：
- 新增 `services/trading_calendar.py`：内置2026年A股交易日历
- 或集成交易日历API（如 exchange_calendars 库）
- 在 Phase 1.2 交易引擎任务中补充此依赖

### 2.3 收益指标计算在Phase中定位模糊

**PRD 依据**：§4.3.4 定义了6个核心收益指标（总收益率、日收益率、最大回撤、夏普比率、胜率、盈亏比）。

**当前问题**：
- IMPLEMENTATION_PLAN 中 `B-1.2.19 PortfolioService` 标注在Phase 1.2，预估8h
- 但Phase 1.3验收标准中又提到"收益指标可查看（收益率/夏普/回撤/胜率）"
- 定位重叠，开发者无法判断应在哪个Phase完成此功能

**建议**：
- 明确：Phase 1.2 完成**计算逻辑**（后端 PortfolioService）
- Phase 1.3 完成**展示层**（前端图表、仪表盘集成）
- 在两个Phase的验收标准中分别注明

### 2.4 AI职级晋升的"无成本版"规则未定义

**PRD 依据**：§4.4.4 职级晋升体系定义了实习生→经理（Lv.6）→合伙人（Lv.12）的路径。

**DELIVERY_PLAN 依据**：Local版为"无成本版"——仅能力差异，无工资约束。

**当前问题**：
- ARCHITECTURE.md 中有 `AgentLevel` 枚举和 `PromotionService` 的提及
- 但**没有**定义"无成本版"的具体规则：等级如何计算？没有工资/交易日概念时如何升级？
- IMPLEMENTATION_PLAN `B-1.2.17 PromotionService` 仅标注"等级升级、晋升判断"，缺少Local特化说明

**建议**：
- 在ARCHITECTURE.md中明确Local版的晋升简化规则：
  - 等级计算：基于交易日数（每5个交易日+1级），或基于交易次数
  - 晋升条件：等级达标即可晋升，无工资前置条件
  - 激励档位：解锁后直接可用，无成本约束

### 2.5 新闻/舆论采集来源在架构中未定义

**PRD 依据**：§3.2 功能交付矩阵中 Local 标记为"✅ 完整"的新闻/舆论。

**当前问题**：
- ARCHITECTURE.md §3.1 目录结构中有 `services/news_collector.py`
- 但**没有**像数据源系统那样定义新闻数据的具体来源（哪些财经网站？哪些社交媒体？）
- IMPLEMENTATION_PLAN `B-1.3.11 新闻采集`（12h）和 `B-1.3.12 舆论采集`（12h）仅有"复用v0.9逻辑"的笼统描述

**建议**：
- 在ARCHITECTURE.md中补充新闻数据源架构（类似行情数据源的设计）
- 至少定义：东方财富新闻、新浪财经新闻、同花顺资讯等来源
- 舆论采集来源：雪球、东方财富股吧等

## 三、架构过度设计（🟡 中优先级）

### 3.1 六数据源全量复刻可能得不偿失

**现实考量**：
- ARCHITECTURE.md 用了约500行代码定义六数据源 + DataSourceRouter + 熔断器 + 三层缓存 + 数据质量引擎
- IMPLEMENTATION_PLAN 中数据采集系统共计约 **69h** 工时（B-1.2.3 ~ B-1.2.8），占Phase 1.2总工时的约40%
- 对于**单用户自用版**，同时维护6个爬虫适配器的成本极高（反爬策略变化频繁）

**与核心目标的距离**：
- consultation-material.html 的核心合规论点是"策略验证工具"，不依赖于数据源数量
- PRD的北极星指标是"AI交易员创建数"，数据源精度不是差异化价值

**建议**：
- Phase 1.2 仅实现 **2个实时源（新浪+腾讯）+ 1个历史源（AkShare）+ CSV离线**
- DataSourceRouter 保留设计，但简化为2源failover而非6源权重
- 东方财富、Baostock、Tushare 延后到Phase 1.3或独立迭代
- 预计节省 **30-40h** 工时，可重新分配到合规层和策略粒度检测

### 3.2 三层缓存架构过重

**当前设计**：L1内存（10s TTL）→ L2 SQLite → L3远程数据源

**单用户场景实际需求**：
- 单用户不存在缓存命中率优化的需求
- SQLite本身就是本地存储，再加L2缓存层等于双重缓存
- 5秒推送间隔下，内存缓存的10s TTL意义有限

**建议**：
- 简化为 **内存 + 远程** 两层即可
- SQLite作为持久化存储（日K线等历史数据），不作为缓存层
- 移除DataCacheManager的L2逻辑，减少代码复杂度

### 3.3 WebSocket心跳和重连机制过度工程化

**当前设计**：15秒心跳、指数退避重连、断线数据补偿（行情+交易+决策三类补偿）

**单用户场景实际需求**：
- `localhost` 连接，网络中断概率极低
- 即使断开，刷新页面即可恢复
- 断线数据补偿涉及三种消息类型的缓存，增加了大量代码复杂度

**建议**：
- 心跳保持（防止浏览器关闭连接），但简化为30秒间隔
- 重连策略保留，但去除数据补偿（重连后重新订阅即可获取最新数据）
- 省出的精力用于核心业务功能

## 四、实施计划缺陷（🟢 低-中优先级）

## 七、结论

当前架构文档的技术深度优秀，但存在一个系统性盲区：**合规层设计的缺失**。

consultation-material.html 作为合规咨询材料，提出了产品生存的底线设计——策略输入边界、免责声明、工具vs服务定位。这些在PRD中已冻结为具体规格（粒度分级、合规声明、术语规范）。但在架构和实施计划中，**合规不是"附加功能"，而是需要贯穿API层、Service层、前端组件的横切关注点**。

建议将合规层设计提升为与数据源系统、AI适配器同等重要的架构模块，在Phase 1.2中引入基础合规框架，Phase 1.3中完善粒度检测。
