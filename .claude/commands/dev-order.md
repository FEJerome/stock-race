# 文档驱动开发命令

**指令：** 执行指定的项目系统工作，严格遵循文档流程与规范约束，并确保完整的文档留痕。

## 核心原则

1.  **文档优先**：所有工作必须以现有文档为基础，遵循既定规范
2.  **规范遵从**：严格执行项目文档中定义的流程和标准
3.  **留痕原则**：任何工作必须在文档中留下清晰痕迹，便于后续智能体快速定位
4.  **上下文持久化**：通过文档结构将项目上下文可靠持久化
5.  **效率优化**：通过文档导航减少重复工作，降低token消耗
6.  **测试驱动**：采用测试驱动开发（TDD）方式，先编写测试脚本，再开发功能代码，测试通过方认为开发完成

## 文档导航与规范遵循

### 1. 文档体系访问
1.  **从导航中心开始**：通过 `CLAUDE.md` 了解项目文档分层结构
2.  **定位相关文档**：根据任务类型，从以下路径获取规范：
    - **开发规范**：`docs/development/` 目录
    - **架构规范**：`docs/architecture/` 目录
    - **智能体协作**：`docs/agents/` 目录
    - **使用指南**：`docs/usage/` 目录
    - **服务模块文档**：`docs/modules/<服务名>/` 目录（针对特定服务的文档）

### 2. 服务模块文档结构

每个服务模块必须在 `docs/modules/<服务名>/` 目录下维护以下文档：

| 文件名 | 用途 | 内容要求 | 智能体权限 |
|--------|------|----------|------------|
| **TODO.md** | 代办事项和阻塞条目 | - 列出待开发的功能和任务<br>- 标注外部依赖阻塞的条目<br>- 按优先级排序<br>- 记录开发进度和实现描述 | **/dev-order智能体**：只能阅读和追加<br>**架构师智能体**：可阅读、追加、删除、修改 |
| **TEST_SCRIPTS.md** | 测试脚本管理 | - 测试脚本的面向功能<br>- 测试脚本的功用<br>- 测试脚本文件位置<br>- 测试覆盖范围<br>- 测试脚本状态更新 | **/dev-order智能体**：可自由阅读和修改<br>**架构师智能体**：可自由阅读和修改 |
| **HAVE_DONE.md** | 已完成任务记录 | - 记录已完成的功能和任务<br>- 架构师标注的优化空间<br>- 潜在风险和注意事项 | **/dev-order智能体**：只能阅读<br>**架构师智能体**：可阅读和更新 |

### 2. 规范约束执行
在执行任何任务前，必须：
1.  **查阅相关规范**：了解任务类型对应的所有规范文档
2.  **遵循既定流程**：严格按照文档中定义的流程执行
3.  **保持一致性**：确保工作成果与项目整体风格一致

## 文档留痕与上下文持久化

### 1. 工作留痕
1.  **实时更新**：工作过程中实时更新相关文档
2.  **结构化记录**：将工作内容按规范格式记录到对应文档
3.  **变更说明**：清晰记录所有变更的原因、内容和影响

### 2. 产出物管理
1.  **规范存储**：将新产出物存储到项目规范定义的对应目录
2.  **目录结构**：严格遵循 `CLAUDE.md` 中定义的目录结构
3.  **索引更新**：确保新内容在文档索引中可被发现

### 3. 上下文持久化
1.  **分层存储**：按文档分层结构存储信息，避免信息过载
2.  **链接导航**：使用文档链接建立导航关系，便于快速访问
3.  **摘要生成**：为重要工作生成简短摘要，减少后续阅读成本

### 2. 测试驱动开发流程（TDD）

#### 2.1 TDD 工作循环
所有功能开发必须遵循以下测试驱动开发流程：

```
┌─────────────────────────────────────────────────────────────┐
│                    TDD 工作循环                              │
├─────────────────────────────────────────────────────────────┤
│                                                              │
│  1. 编写测试（Red）                                           │
│     ├─ 根据需求文档编写测试用例                               │
│     ├─ 测试应该覆盖正常流程、边界条件、异常情况                │
│     └─ 运行测试，确认失败（红色）                              │
│                                                              │
│  2. 编写代码（Green）                                         │
│     ├─ 编写最少量的代码使测试通过                             │
│     ├─ 不追求完美，只求测试通过                                │
│     └─ 运行测试，确认通过（绿色）                              │
│                                                              │
│  3. 重构优化（Refactor）                                      │
│     ├─ 优化代码结构，提高可读性和可维护性                      │
│     ├─ 保持测试通过                                           │
│     └─ 确保重构不改变功能行为                                 │
│                                                              │
│  4. 完成确认                                                  │
│     ├─ 所有测试通过                                           │
│     ├─ 代码符合开发规范                                        │
│     ├─ 文档已更新                                             │
│     └─ 功能可以交付                                           │
│                                                              │
└─────────────────────────────────────────────────────────────┘
```

#### 2.2 TDD 执行步骤

**步骤1：需求分析与测试设计**
1. 阅读 `docs/modules/<服务名>/TODO.md` 了解任务需求
2. 设计测试用例，包括：
   - 正常流程测试（Happy Path）
   - 边界条件测试（Boundary Cases）
   - 异常情况测试（Error Cases）
   - 性能测试（Performance Tests，如需要）
3. 在 `docs/modules/<服务名>/TEST_SCRIPTS.md` 中记录测试脚本规划

**步骤2：编写测试脚本**
1. 在项目的测试目录中创建测试文件
2. 按照测试用例编写测试代码
3. 运行测试，确认所有测试失败（Red阶段）
4. 更新 `docs/modules/<服务名>/TEST_SCRIPTS.md` 记录测试脚本位置和内容

**步骤3：编写功能代码**
1. 编写最少量的代码使测试通过
2. 运行测试，确认测试通过（Green阶段）
3. 如测试未通过，调整代码直到通过
4. 重复此过程直到所有测试通过

**步骤4：重构与优化**
1. 在保持测试通过的前提下优化代码
2. 提高代码可读性、可维护性
3. 确保代码符合项目开发规范
4. 运行测试，确认重构后测试仍然通过

**步骤5：完成确认**
1. 所有测试用例通过
2. 代码已提交到版本控制
3. **提交到工作树分支**：将代码提交至对应服务的工作树分支，工作树名称即为服务名
4. **追加更新 `docs/modules/<服务名>/TODO.md`**：记录任务的开发进度和实现简单描述
5. **更新 `docs/modules/<服务名>/TEST_SCRIPTS.md`**：确保测试脚本状态与实际状态匹配
6. **阅读 `docs/modules/<服务名>/HAVE_DONE.md`**：获取之前的开发信息和架构师标注
7. **注意**：删除 `TODO.md` 条目和更新 `HAVE_DONE.md` 的操作只能由架构师智能体执行

### 3. 效率优化
- **精准定位**：通过文档导航快速定位所需信息
- **避免重复**：先检查现有文档，避免重复工作
- **按需加载**：仅加载与当前任务相关的文档内容
- **分段处理**：复杂任务分解为小步骤，减少一次性上下文长度
- **测试先行**：通过测试驱动减少返工，提高开发效率

### 4. 完成确认
任务完成后，必须：
1.  **测试通过确认**：所有相关测试用例必须通过
2.  **留痕确认**：确认所有工作都已在文档中留下清晰痕迹
3.  **导航验证**：验证新内容可以通过文档导航系统被发现
4.  **摘要生成**：为本次工作生成简短摘要，便于后续智能体快速了解
5.  **文档更新**：
   - ✅ **可执行**：追加更新 `TODO.md` 记录开发进度
   - ✅ **可执行**：更新 `TEST_SCRIPTS.md` 确保状态匹配
   - ✅ **可执行**：阅读 `HAVE_DONE.md` 获取信息
   - ❌ **不可执行**：删除 `TODO.md` 条目（仅架构师可执行）
   - ❌ **不可执行**：更新 `HAVE_DONE.md`（仅架构师可执行）
6.  **测试归档**：测试脚本和测试报告已归档到指定目录
